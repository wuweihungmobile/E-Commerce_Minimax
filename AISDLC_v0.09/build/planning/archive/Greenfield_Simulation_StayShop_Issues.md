# Greenfield SOP 模擬問題清單 - StayShop（電商+民宿融合系統）

**模擬日期**: 2026-03-23
**模擬系統**: StayShop - 專業電子商務與民宿管理融合系統
**技術棧**: React(Next.js) + Spring Boot + PostgreSQL
**平台**: Web + Android + macOS（Type A 共享後端）
**模擬目的**: 以雙領域融合系統（電商+民宿）壓力測試 Greenfield SOP，發現不合理、錯誤、遺漏或需改進之處
**特色情境**: 雙業務領域融合、時間維度庫存（房間可用日期）、季節性流量

## 🔴 Critical（2 項）

### #1 缺少多領域融合架構識別指引（Stage 1）
- **位置**: Stage 1 步驟 1.2（line ~319-338）
- **問題**: 多平台快速識別引導僅按「平台」分類（Type A/B/C/D），未考慮「多業務領域融合」的架構維度。電商+民宿共用後端時，需在 Stage 1 就識別「領域邊界」，避免後續架構設計時才發現領域耦合問題。
- **影響**: 雙領域系統在 Stage 3-5 才發現需要領域分離，導致大量返工。
- **建議**: 在多平台快速識別引導下方新增「多領域融合識別引導」，包含: 單領域/雙領域/多領域的快速判斷表和 AI 確認問題。

### #2 缺少時間維度庫存（訂房/日曆）的資料庫設計模式（Stage 5）
- **位置**: Stage 5 步驟 5.2.2（line ~2499-2700）
- **問題**: 資料庫設計章節僅涵蓋「數量型庫存」（商品庫存 quantity）和 Object DB。對於民宿/旅宿/預約類系統，庫存是「時間維度」的（特定日期的房間可用性），需要完全不同的 Schema 設計模式：日期區間查詢、可用性矩陣、季節定價表、防止雙重預訂的並發控制。這在經銷存模擬中不會暴露，但在任何含「預約/訂位/租賃」的系統中是核心問題。
- **影響**: 開發團隊缺乏指引，可能設計出效能低落或有並發缺陷的訂房系統。
- **建議**: 在資料庫設計章節新增「時間維度庫存設計模式（Calendar-based Inventory）」子節，包含日期可用性表設計、防止雙重預訂的樂觀鎖/悲觀鎖範例、季節定價表 Schema。

## 🟠 High（8 項）

### #3 產業領域業務規則缺少旅宿/民宿業（Stage 2）
- **位置**: Stage 2 步驟 2.2 業務規則確認（line ~723-734）
- **問題**: 常見產業領域業務規則提示表涵蓋 6 個產業（經銷存、電商、金融、醫療、製造、物流），但缺少「旅宿/民宿/飯店業」。民宿有獨特業務規則：入住/退房時間規則、取消政策（依入住前天數不同退款比例）、季節定價、連續住宿折扣、房態管理（可售/維修/保留）、OTA 渠道管理（Booking.com/Airbnb 同步）。
- **建議**: 新增「旅宿/民宿/飯店」產業列至業務規則表，包含核心規則列舉。

### #4 缺少跨領域 MVP 定義策略（Stage 4）
- **位置**: Stage 4 步驟 4.2（line ~1572-1698）
- **問題**: MVP 定義使用 RICE + Kano 對功能清單排序，但雙領域系統需要先「按領域界定 MVP 範圍」，再合併優先級。例如：電商 MVP 可能是商品瀏覽+購物車+結帳，民宿 MVP 可能是房源展示+訂房+入住，兩者合併後的 Phase 1 範圍需要跨領域協調。
- **建議**: 在 MVP 定義模板前新增「多領域 MVP 策略」指引，說明按領域分別評估再合併的方法。

### #5 缺少訂房/日曆型 Epic 拆解範例（Stage 6）
- **位置**: Stage 6 步驟 6.2.4（line ~3595-3677）
- **問題**: Epic 拆解範例有電商搜尋（EPIC-002）和進貨驗收流程（EPIC-005），但缺少「預約/訂房」類型的 Epic 範例。訂房流程的 User Story 拆分方式與一般 CRUD 不同：需要日期選擇 → 可用性檢查 → 價格計算（含季節/連住折扣）→ 庫存鎖定 → 付款 → 確認。日期維度增加了拆分複雜度。
- **建議**: 新增一個「EPIC-006: 訂房與入住管理流程」範例，展示日曆型 User Story 拆分。

### #6 硬體整合問題缺少 IoT/智慧設備類別（Stage 2）
- **位置**: Stage 2 步驟 2.3 H1-H12 硬體整合問題（line ~773-788）
- **問題**: 硬體整合問題涵蓋 POS、電子秤、RFID、標籤印表機等零售/倉儲設備，但缺少民宿/旅宿常見的 IoT 設備：智慧門鎖（密碼/NFC）、自助入住機（Kiosk）、房間感應器（溫度/門窗）、智慧家電（空調/燈光控制）。
- **建議**: 新增 H13-H16 IoT/智慧設備整合問題。

### #7 跨領域依賴類型未納入 Sprint 依賴管理（Stage 7）
- **位置**: Stage 7 步驟 7.2.1.1（line ~4362-4403）
- **問題**: 依賴類型定義了 5 種（技術、資料、業務、測試、環境），但缺少「跨領域依賴（Cross-Domain Dependency）」。雙領域系統中，領域間有交叉依賴：電商會員積分可用於民宿折扣、民宿客戶可在電商購買備品、統一客戶檔案跨兩個領域共用。
- **建議**: 新增第 6 種依賴類型「跨領域依賴」，含範例和緩解策略。

### #8 變更影響分析缺少跨領域影響範例（Stage 10）
- **位置**: Stage 10 步驟 10.2.1（line ~7163-7219）
- **問題**: CIA 常見修改操作影響範例全部是單領域（商品單價、客戶等級、庫存數量）。雙領域系統的跨領域變更影響更複雜：修改會員等級 → 影響電商折扣率 AND 民宿優惠房價；修改積分規則 → 影響電商消費積點 AND 民宿入住積點。
- **建議**: 在 CIA 範例表中新增 2-3 個跨領域影響範例。

### #9 軟刪除策略缺少「未來承諾」處理指引（Stage 5）
- **位置**: Stage 5 軟刪除策略（line ~2653-2714）
- **問題**: 軟刪除決策指引考慮「歷史引用」（歷史訂單、價格追溯），但未考慮「未來承諾」。例如：軟刪除一個民宿房型時，該房型可能有未來 30 天內的已確認訂房。需要先處理未來訂單（遷移至其他房型或通知取消）再軟刪除。電商也有類似場景：下架商品時有未出貨的預購訂單。
- **建議**: 在刪除策略決策指引表中新增「未來承諾檢查」欄位，在級聯軟刪除範例中新增預約/預購處理範例。

### #10 缺少多領域 API 模組化設計指引（Stage 5）
- **位置**: Stage 5 步驟 5.2.3（line ~2718-2912）和步驟 5.2.5（line ~3193）
- **問題**: API 設計指引假設單一領域的 API 結構。雙領域系統需要決定 API 模組化策略：統一 API 路徑（`/api/v1/products`, `/api/v1/rooms`）vs 領域前綴（`/api/v1/ecommerce/products`, `/api/v1/bnb/rooms`）vs 微服務（各領域獨立服務）。API 版本管理也需考慮各領域獨立演進。
- **建議**: 新增「多領域 API 模組化策略」指引，含路徑設計範例和領域獨立版本管理建議。

## 🟡 Medium（10 項）

### #11 缺少季節性/事件驅動擴展性指引（Stage 5）
- **位置**: Stage 5 效能需求量化設計（line ~2914-3118）
- **問題**: 效能指標設計使用固定併發數目標，未考慮「季節性尖峰」。電商有雙 11/黑色星期五，民宿有旅遊旺季/連假，融合系統可能雙重尖峰疊加。需要季節性 Auto Scaling 策略。
- **建議**: 在效能指標設計流程中新增「季節性/事件驅動尖峰場景」識別步驟和彈性擴展策略。

### #12 跨平台整合測試缺少跨領域場景範例（Stage 10）
- **位置**: Stage 10 步驟 10.3.1（line ~7231-7293）
- **問題**: 跨平台端到端測試範例全部在庫存管理單一領域。雙領域系統需要跨領域端到端測試：如「Web 訂房 → Android 掃碼入住 → 入住觸發電商歡迎禮包推送 → macOS 報表顯示合併營收」。
- **建議**: 新增一個跨領域端到端測試場景範例。

### #13 缺少共用實體建模指引（Stage 5）
- **位置**: Stage 5 資料庫設計（line ~2499-2570）
- **問題**: 雙領域系統中「客戶/會員」是共用實體（同一人既是電商買家又是民宿房客），但「商品」和「房間」是各自領域的獨立實體。SOP 未提供「共用 vs 獨立實體」的建模決策指引。
- **建議**: 在資料庫設計章節新增「多領域共用實體建模」指引，含決策表和 Schema 範例。

### #14 跨領域一致性檢查缺失（Stage 9）
- **位置**: Stage 9 步驟 9.2（line ~7028-7070）
- **問題**: 文檔一致性檢查驗證追蹤鏈（F→BR→EPIC→US→AC→API），但未涵蓋跨領域資料模型一致性。例如：電商的「客戶」和民宿的「客戶」是否指向同一資料模型？共用欄位定義是否一致？
- **建議**: 在一致性檢查清單中新增「跨領域資料模型一致性檢查」項目。

### #15 缺少多領域部署回滾策略（Stage 11）
- **位置**: Stage 11 步驟 11.2 回滾策略（line ~7436-7476）
- **問題**: 回滾策略是系統級（整體回滾），未考慮領域獨立回滾。如果電商模組更新出問題，是否可以只回滾電商而不影響民宿服務？需要依架構決定（單體 vs 微服務）。
- **建議**: 新增「多模組/多領域回滾策略」指引，根據架構類型（單體/微服務）提供不同回滾方案。

### #16 缺少多領域 CI/CD Pipeline 策略（Stage 8）
- **位置**: Stage 8 步驟 8.2 CI/CD Pipeline（line ~6600+）
- **問題**: CI/CD 範例是單一應用的 Pipeline。雙領域系統如果採用微服務架構，需要獨立的 Pipeline 加上跨服務整合測試。即使是單體架構，也需要按領域模組設定測試範圍。
- **建議**: 新增「多模組/微服務 CI/CD 策略」指引，含 Monorepo 和 Multi-repo 的 Pipeline 設計。

### #17 NFR 缺少雙領域混合流量分析引導（Stage 2）
- **位置**: Stage 2 Web/Backend NFR 引導問題（line ~668-700）
- **問題**: 併發量引導問題問「預估同時在線使用者數」，但雙領域系統的流量模式截然不同：電商是瀏覽→購買的短交易，民宿是搜尋→比價→訂房的長 Session。混合流量的基線和尖峰需分別估算再合併。
- **建議**: 在併發與擴展性問題中新增「多領域混合流量分析」引導問題。

### #18 缺少 OTA 渠道整合引導（Stage 2）
- **位置**: Stage 2 整合與外部系統問題（line ~689-694）
- **問題**: 整合問題涵蓋 ERP、電子發票、Email/SMS，但缺少旅宿業常見的 OTA 渠道整合（Booking.com/Airbnb/Agoda API、Channel Manager 頻道管理）。OTA 整合是民宿系統的核心需求。
- **建議**: 在整合確認問題中新增「OTA/訂房平台渠道整合」引導問題。

### #19 入住/退房流程缺少 Epic 範例（Stage 6）
- **位置**: Stage 6 步驟 6.2.4（line ~3679-3698）
- **問題**: 業務流程 Epic 範例有「進貨驗收與入庫」（製造/零售），但缺少「入住與退房流程」（旅宿業）。入住流程包含：身份驗證 → 房間分配 → 門鎖密碼/鑰匙發放 → 入住確認 → 退房 → 房間檢查 → 押金退還。有審核節點和狀態流轉。
- **建議**: 新增入住退房 Epic 範例，展示旅宿業務流程的 User Story 拆分。

### #20 缺少預約並發衝突解決指引（Stage 5/10）
- **位置**: Stage 5 資料庫設計 / Stage 10 開發實施
- **問題**: 民宿訂房是典型的「最後一間房」並發問題（類似電商的「最後一件庫存」）。SOP 中未提供預約系統的並發衝突解決策略（樂觀鎖 vs 悲觀鎖 vs 預扣機制）。電商庫存預扣已在 IMP-02 的級聯軟刪除中略提，但預約系統的時間維度並發更複雜。
- **建議**: 在資料庫設計或開發實施章節新增「預約/庫存並發控制策略」指引。

## 🟢 Low（5 項）

### #21 多領域技術選型中缺少預約引擎選型指引（Stage 3）
- **位置**: Stage 3 技術棧評估表（line ~1266-1376）
- **問題**: 技術棧評估涵蓋前端框架、後端框架、資料庫等，但缺少「預約/日曆引擎」的選型指引（自建 vs 第三方如 cal.com、Calendly API）。
- **建議**: 在技術選項中提及預約引擎作為可選技術組件。

### #22 跨領域垂直切分指引不足（Stage 6）
- **位置**: Stage 6 垂直切分技巧（line ~3446-3453）
- **問題**: 垂直切分維度包含「按角色/操作/資料/流程/複雜度」，但缺少「按領域」切分維度。融合系統中部分功能橫跨兩個領域（如：統一客戶檔案、跨領域報表），需要特殊的切分策略。
- **建議**: 在垂直切分技巧表中新增「按業務領域」切分維度。

### #23 Stage 1 情境識別缺少領域數量問題
- **位置**: Stage 1 步驟 1.2（line ~319-324）
- **問題**: 情境識別問題問「專案類型、專案規模、團隊情況」，但缺少「業務領域數量」問題。單領域和多領域系統的規劃複雜度差異極大。
- **建議**: 在情境識別問題中新增「專案涉及幾個業務領域？」引導問題。

### #24 缺少合併營收報表設計指引（Stage 5/6）
- **位置**: Stage 5 架構設計 / Stage 6 User Story
- **問題**: 融合系統需要合併報表（電商營收 + 民宿營收的整合儀表板），涉及跨領域資料聚合。SOP 未提及跨領域報表設計模式。
- **建議**: 可在 API 設計或 User Story 範例中提及跨領域報表場景。

### #25 缺少多領域資料歸檔策略差異指引（Stage 5）
- **位置**: Stage 5 軟刪除策略（line ~2653-2700）
- **問題**: 不同領域的資料保留政策不同：電商交易紀錄需保留 7 年（稅務），民宿住客資料可能受個資法限制需定期清除。統一系統中需要差異化的歸檔策略。
- **建議**: 在資料保留政策指引中提及多領域差異化歸檔需求。

## 🎯 結論

本次模擬發現 Greenfield SOP 的核心假設是「**單一業務領域**」系統。當面對「**多領域融合系統**」（如電商+民宿）時，以下方面存在系統性缺口：

1. **領域識別**: 沒有在早期識別多領域融合的機制
2. **領域建模**: 缺少共用 vs 獨立實體的建模指引
3. **日曆/預約模式**: 缺少時間維度庫存的設計模式
4. **跨領域協調**: MVP、依賴、測試、部署都缺少跨領域維度
5. **旅宿業覆蓋**: 業務規則、Epic 範例、硬體整合缺少旅宿業

建議透過新增「多領域融合」專節來系統性解決這些問題，而非逐項零散修補。
