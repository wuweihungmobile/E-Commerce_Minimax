# 錯誤恢復機制指南 / Error Recovery Guide

**版本 / Version**: v0.09
**建立日期 / Created**: 2025-11-10
**文檔目的 / Purpose**: 定義 AISDLC 九大情境中常見錯誤場景的檢測與恢復機制

---

## 📋 文檔概述 / Document Overview

### 目的 / Purpose

本指南提供：
1. **錯誤分類體系** - 按嚴重程度和影響範圍分類
2. **檢測機制** - 如何及早發現潛在錯誤
3. **恢復策略** - 針對不同錯誤的恢復步驟
4. **預防措施** - 如何避免常見錯誤發生

### 錯誤恢復原則 / Recovery Principles

1. **🔴 及早檢測 (Early Detection)** - 在錯誤擴散前發現
2. **🟡 快速隔離 (Quick Isolation)** - 防止影響其他模組
3. **🟢 系統性恢復 (Systematic Recovery)** - 有步驟地恢復,不造成二次傷害
4. **📝 記錄與學習 (Learn & Document)** - 記錄錯誤原因,避免重複

## 🚨 錯誤分類體系 / Error Classification

### 按嚴重程度分類

| 等級 | 名稱 | 影響 | 恢復時效 | 範例 |
|-----|------|------|---------|------|
| **P0** | 阻斷性錯誤 | 完全無法繼續 | 立即處理 | 關鍵文檔遺失、框架載入失敗 |
| **P1** | 嚴重錯誤 | 嚴重影響進度 | 4 小時內 | 需求理解錯誤、架構設計缺陷 |
| **P2** | 中等錯誤 | 需要修正但可繼續 | 1 天內 | 文檔格式錯誤、測試案例不足 |
| **P3** | 輕微錯誤 | 影響品質但不阻斷 | 1 週內 | 命名不一致、文檔細節缺失 |

### 按錯誤類型分類

#### 1. 文檔類錯誤 (Document Errors)
- **D1**: 關鍵文檔遺失 (PRD/FRD/SRD/AC)
- **D2**: 文檔內容錯誤或自相矛盾
- **D3**: 文檔版本混亂
- **D4**: 文檔追蹤鏈斷裂

#### 2. 需求類錯誤 (Requirement Errors)
- **R1**: 需求理解錯誤
- **R2**: 需求變更未追蹤
- **R3**: 需求優先級錯誤
- **R4**: 需求範圍蔓延 (Scope Creep)

#### 3. 設計類錯誤 (Design Errors)
- **S1**: 架構設計缺陷
- **S2**: API 設計不一致
- **S3**: 資料模型錯誤
- **S4**: 效能設計不足

#### 4. 測試類錯誤 (Testing Errors)
- **T1**: 測試覆蓋率不足
- **T2**: 測試案例錯誤
- **T3**: 測試環境問題
- **T4**: 測試數據缺失

#### 5. 流程類錯誤 (Process Errors)
- **P1**: 跳過人機協作確認點 🔴
- **P2**: 情境轉換過早
- **P3**: 並行衝突
- **P4**: 循環轉換未解決

#### 6. 工具類錯誤 (Tool Errors)
- **W1**: Agent 載入失敗
- **W2**: Workflow 觸發錯誤
- **W3**: 文檔模板錯誤
- **W4**: 整合工具失效

## 🔍 通用錯誤檢測機制 / Universal Detection Mechanisms

### 自動檢測檢查點 (Automated Checkpoints)

每個情境的 SOP 都應包含以下檢查點：

#### 1️⃣ 階段入口檢查 (Phase Entry Check)
```yaml
檢查項目:
  - [ ] 前一階段產出文件完整性
  - [ ] 必要材料是否齊全
  - [ ] Agent 角色正確載入
  - [ ] 情境上下文正確設定

觸發時機: 每個新階段開始前
自動化程度: 80% (AI 自動檢查 + 人工確認)
```

#### 2️⃣ 人機協作確認點檢查 (Collaboration Checkpoint)
```yaml
檢查項目:
  - [ ] 人類是否已確認關鍵決策 🔴
  - [ ] 確認時間戳記是否記錄
  - [ ] 確認內容是否明確
  - [ ] 是否有歧義需要澄清

觸發時機: 每個 🔴 標記的確認點
自動化程度: 50% (AI 提醒 + 人工確認)
```

#### 3️⃣ 文檔一致性檢查 (Document Consistency Check)
```yaml
檢查項目:
  - [ ] PRD ↔ FRD 需求一致性
  - [ ] FRD ↔ SRD 設計一致性
  - [ ] SRD ↔ API 規格一致性
  - [ ] AC ↔ AT 測試追蹤性

觸發時機: 文檔更新後、階段結束前
自動化程度: 70% (AI 交叉檢查 + 人工審查)
```

#### 4️⃣ 品質閘門檢查 (Quality Gate Check)
```yaml
檢查項目:
  - [ ] 產出文件符合模板要求
  - [ ] 所有必填欄位已完成
  - [ ] 文檔追蹤鏈完整
  - [ ] 利害關係人已批准

觸發時機: 階段結束前、情境轉換前
自動化程度: 60% (AI 格式檢查 + 人工品質審查)
```

## 🛠️ 情境別錯誤場景與恢復策略 / Scenario-Specific Recovery

### 1️⃣ Greenfield - 新專案開發

#### 常見錯誤場景

##### 錯誤 G1: 需求模糊不清 (R1 - P1)

**症狀**:
```
⚠️ 檢測到需求模糊:
- PRD 缺少具體使用場景
- 功能需求描述抽象
- 驗收條件 (AC) 無法量化
```

**檢測時機**: 階段 2 需求分析完成時

**恢復步驟**:
```
步驟 1: 暫停當前流程 🔴
步驟 2: 回到需求澄清階段
  - 使用「5W1H」方法重新訪談
  - 建立具體使用場景 (User Story Mapping)
  - 與利害關係人確認範例情境
步驟 3: 更新 PRD/FRD
  - 補充具體使用場景
  - 量化驗收條件
  - 更新文檔版本號
步驟 4: 重新進行 Peer Review (SA ↔ BA)
步驟 5: 利害關係人確認後繼續 🔴
```

**預防措施**:
- ✅ 使用需求收集模板 (包含使用場景欄位)
- ✅ 在需求分析階段安排至少 2 次澄清會議
- ✅ 要求每個功能至少有 3 個具體範例

**預計恢復時間**: 0.5-1 天

---

##### 錯誤 G2: 技術選型錯誤 (S1 - P1)

**症狀**:
```
⚠️ 技術選型風險:
- 選擇的技術棧團隊不熟悉
- 技術棧不符合效能需求
- 第三方服務成本超出預算
```

**檢測時機**: 階段 3 技術選型確認點 🔴

**恢復步驟**:
```
步驟 1: 停止後續設計 🔴
步驟 2: 重新評估技術選型
  - 召集 SD + Dev-Senior 重新評估
  - 進行技術可行性 PoC (Proof of Concept)
  - 重新計算 TCO (Total Cost of Ownership)
步驟 3: 提供替代方案
  - 至少提供 2-3 個替代技術棧
  - 對比分析表 (學習曲線、成本、效能、社群支援)
步驟 4: 利害關係人確認新方案 🔴
步驟 5: 更新 Tech Stack Selection Report
```

**預防措施**:
- ✅ 技術選型前先進行團隊技能盤點
- ✅ 對關鍵技術進行 PoC 驗證
- ✅ 包含備選方案 (Plan B)

**預計恢復時間**: 1-2 天

---

##### 錯誤 G3: PRD/FRD 追蹤鏈斷裂 (D4 - P2)

**症狀**:
```
⚠️ 文檔追蹤鏈檢查失敗:
- FRD 功能無法追溯到 PRD
- User Story 缺少 FRD 引用
- AC 缺少 User Story ID
```

**檢測時機**: 階段 4 需求驗證與文件化完成時

**恢復步驟**:
```
步驟 1: 執行追蹤鏈審查
  - 使用追蹤矩陣 (Traceability Matrix)
  - 標記所有斷裂點
步驟 2: 補充追蹤連結
  - 為每個 FRD 功能補充 PRD 引用
  - 為每個 User Story 補充 FRD 引用
  - 為每個 AC 補充 User Story ID
步驟 3: 更新文檔版本
步驟 4: 重新執行一致性檢查
```

**預防措施**:
- ✅ 使用文檔模板 (包含追蹤欄位)
- ✅ 在文檔產出時即時建立追蹤連結
- ✅ 定期執行追蹤鏈檢查 (每個階段結束時)

**預計恢復時間**: 2-4 小時

---

### 2️⃣ Brownfield - 既有系統分析

#### 常見錯誤場景

##### 錯誤 B1: 影響範圍評估錯誤 (R3 - P1)

**症狀**:
```
⚠️ 影響範圍低估:
- 變更影響到未評估的模組
- 相依性分析不完整
- 資料遷移複雜度被低估
```

**檢測時機**: 階段 2 代碼分析與影響評估完成時

**恢復步驟**:
```
步驟 1: 停止開發計畫 🔴
步驟 2: 重新執行影響分析
  - 使用 Code-Analyzer Agent 深度掃描
  - 建立完整相依性圖 (Dependency Graph)
  - 識別所有間接影響
步驟 3: 擴大測試範圍
  - 更新回歸測試計畫
  - 增加整合測試案例
步驟 4: 調整時程估算
  - 重新評估開發時間
  - 與利害關係人溝通時程變更 🔴
步驟 5: 更新影響分析報告
```

**預防措施**:
- ✅ 使用自動化工具分析代碼相依性
- ✅ 進行至少 2 輪影響分析 (粗評估 + 細評估)
- ✅ 預留 30% 緩衝時間應對未預期影響

**預計恢復時間**: 1-2 天

---

##### 錯誤 B2: 測試覆蓋率不足 (T1 - P2)

**症狀**:
```
⚠️ 測試風險高:
- 現有系統測試覆蓋率 < 50%
- 關鍵業務邏輯缺少測試
- 變更區域無回歸測試
```

**檢測時機**: 階段 3 需求驗證與文件化時

**恢復步驟**:
```
步驟 1: 評估測試風險
  - 識別高風險模組 (複雜度高、業務核心)
  - 計算所需測試數量
步驟 2: 制定測試補強計畫
  - 優先補強高風險模組測試
  - 為變更區域建立完整測試套件
步驟 3: 執行測試補強
  - 安排 QA + Dev 並行補強
  - 目標: 關鍵路徑測試覆蓋率 ≥ 80%
步驟 4: 更新測試計畫文件
```

**預防措施**:
- ✅ 在分析階段即評估測試現況
- ✅ 將測試補強納入專案時程
- ✅ 建立測試優先級矩陣 (風險 × 影響)

**預計恢復時間**: 2-5 天

---

### 3️⃣ Refactoring - 代碼重構

#### 常見錯誤場景

##### 錯誤 F1: 重構範圍過大 (R4 - P1)

**症狀**:
```
⚠️ 重構範圍失控:
- 重構涉及 50%+ 代碼庫
- 預計時程超過 4 週
- 風險無法有效控制
```

**檢測時機**: 階段 1 重構範圍識別完成時

**恢復步驟**:
```
步驟 1: 暫停重構規劃 🔴
步驟 2: 重新評估重構策略
  - 使用「Strangler Fig Pattern」逐步重構
  - 將大重構拆分為多個小重構
  - 建立重構優先級清單
步驟 3: 制定分階段重構計畫
  - Phase 1: 關鍵路徑重構 (1-2 週)
  - Phase 2: 次要模組重構 (2-3 週)
  - Phase 3: 優化與清理 (1-2 週)
步驟 4: 與利害關係人確認分階段計畫 🔴
步驟 5: 更新重構計畫文件
```

**預防措施**:
- ✅ 單次重構時程不超過 3 週
- ✅ 使用「Small Step Refactoring」策略
- ✅ 每個小重構都有明確的驗證標準

**預計恢復時間**: 0.5-1 天

---

##### 錯誤 F2: 重構後測試失敗 (T2 - P1)

**症狀**:
```
⚠️ 回歸測試失敗:
- 30%+ 測試案例失敗
- 發現未預期的行為變更
- 效能劣化
```

**檢測時機**: 階段 3 重構實施與驗證時

**恢復步驟**:
```
步驟 1: 立即停止部署 🔴
步驟 2: 分類失敗原因
  - 測試案例過時 (需更新測試)
  - 行為變更 (需回滾或修正)
  - Bug 引入 (需修復)
步驟 3: 執行回滾或修正
  - 如果失敗率 > 20%: 建議回滾後重新評估
  - 如果失敗率 < 20%: 逐一修正並重測
步驟 4: 加強測試策略
  - 增加測試覆蓋率
  - 加入效能回歸測試
步驟 5: 記錄失敗原因,更新重構檢查清單
```

**預防措施**:
- ✅ 重構前確保測試覆蓋率 ≥ 80%
- ✅ 使用 Feature Flag 控制重構範圍
- ✅ 小步提交,持續集成測試

**預計恢復時間**: 1-3 天

---

### 4️⃣ Integration - 第三方整合

#### 常見錯誤場景

##### 錯誤 I1: API 文檔與實際不符 (D2 - P1)

**症狀**:
```
⚠️ API 整合失敗:
- API 回應格式與文檔不符
- 欄位缺失或型別錯誤
- 錯誤碼未記錄
```

**檢測時機**: 階段 2 整合設計與實作時

**恢復步驟**:
```
步驟 1: 停止整合開發 🔴
步驟 2: 重新進行 API 探索
  - 使用 Postman/curl 實際測試 API
  - 記錄實際回應格式
  - 建立 API 實際行為文檔
步驟 3: 更新整合設計
  - 根據實際行為調整資料映射
  - 增加錯誤處理邏輯
  - 更新 API 規格文件
步驟 4: 重新實作與測試
步驟 5: 與第三方確認 API 文檔問題
```

**預防措施**:
- ✅ 在設計階段即進行 API 實際測試
- ✅ 建立 API Mock Server 用於開發
- ✅ 準備降級方案 (當 API 不可用時)

**預計恢復時間**: 0.5-2 天

---

##### 錯誤 I2: 資料映射錯誤 (S3 - P2)

**症狀**:
```
⚠️ 資料轉換錯誤:
- 資料型別不匹配
- 時區轉換錯誤
- 編碼問題 (UTF-8/Big5)
```

**檢測時機**: 階段 3 整合測試時

**恢復步驟**:
```
步驟 1: 識別所有資料映射點
步驟 2: 建立資料轉換測試案例
  - 邊界值測試
  - 特殊字元測試
  - 空值/NULL 測試
步驟 3: 修正資料映射邏輯
  - 增加型別驗證
  - 統一時區處理
  - 統一編碼格式
步驟 4: 重新執行整合測試
步驟 5: 更新資料映射規格文件
```

**預防措施**:
- ✅ 建立完整的資料映射規格表
- ✅ 使用 Schema Validation 驗證資料格式
- ✅ 建立資料轉換測試套件

**預計恢復時間**: 1-2 天

---

### 5️⃣ Performance - 效能優化

#### 常見錯誤場景

##### 錯誤 P1: 優化後效能劣化 (S4 - P1)

**症狀**:
```
⚠️ 效能優化失敗:
- 優化後效能反而下降
- 某些場景變慢
- 資源使用量增加
```

**檢測時機**: 階段 3 效能優化實施時

**恢復步驟**:
```
步驟 1: 立即回滾優化變更 🔴
步驟 2: 重新分析效能基準
  - 對比優化前後數據
  - 識別劣化原因
  - 檢查是否有副作用
步驟 3: 調整優化策略
  - 重新評估瓶頸點
  - 選擇不同的優化方法
  - 進行 A/B 測試驗證
步驟 4: 小步提交,持續測量
步驟 5: 記錄失敗經驗,更新優化檢查清單
```

**預防措施**:
- ✅ 建立完整的效能基準線
- ✅ 使用 Feature Flag 控制優化範圍
- ✅ 每次優化後立即驗證效能

**預計恢復時間**: 1-3 天

---

##### 錯誤 P2: 瓶頸識別錯誤 (S1 - P2)

**症狀**:
```
⚠️ 優化方向錯誤:
- 優化了非瓶頸環節
- 真正的瓶頸未發現
- 投入產出比低
```

**檢測時機**: 階段 1 效能分析與瓶頸識別時

**恢復步驟**:
```
步驟 1: 停止當前優化工作 🔴
步驟 2: 重新執行效能剖析 (Profiling)
  - 使用多種 Profiling 工具
  - 分析真實使用場景
  - 建立 Flame Graph 視覺化
步驟 3: 重新排序優化優先級
  - 使用 80/20 法則
  - 優先優化瓶頸環節
步驟 4: 重新制定優化計畫
步驟 5: 與利害關係人確認新計畫 🔴
```

**預防措施**:
- ✅ 使用多種 Profiling 工具交叉驗證
- ✅ 在真實環境/數據下分析效能
- ✅ 優先優化 Top 3 瓶頸

**預計恢復時間**: 0.5-1 天

---

### 6️⃣ Security - 安全審查

#### 常見錯誤場景

##### 錯誤 S1: 發現嚴重安全漏洞 (S1 - P0)

**症狀**:
```
🚨 嚴重安全漏洞:
- SQL Injection 漏洞
- XSS 漏洞
- 敏感資料外洩
```

**檢測時機**: 階段 1 安全評估與合規分析時

**恢復步驟**:
```
步驟 1: 立即停止所有開發/部署 🔴🔴🔴
步驟 2: 召集緊急安全會議
  - Security Engineer 主導
  - 所有相關開發人員參與
步驟 3: 評估漏洞影響範圍
  - 是否已在生產環境
  - 影響使用者數量
  - 資料外洩風險
步驟 4: 制定緊急修復計畫
  - 短期: 熱修復 (Hotfix) - 4 小時內
  - 中期: 完整修復 - 1-2 天
  - 長期: 架構調整 - 1-2 週
步驟 5: 執行修復並驗證
步驟 6: 通知利害關係人 (如需要) 🔴
步驟 7: 更新安全檢查清單
```

**預防措施**:
- ✅ 在設計階段即進行威脅建模
- ✅ 使用自動化安全掃描工具
- ✅ 定期進行滲透測試

**預計恢復時間**: 4 小時 - 2 天 (依嚴重程度)

---

### 7️⃣ Testing - 測試執行

#### 常見錯誤場景

##### 錯誤 T1: 測試環境不穩定 (T3 - P2)

**症狀**:
```
⚠️ 測試環境問題:
- 測試頻繁失敗 (Flaky Tests)
- 環境與生產不一致
- 測試資料不完整
```

**檢測時機**: 階段 2 測試執行時

**恢復步驟**:
```
步驟 1: 停止測試執行 🔴
步驟 2: 分析環境問題
  - 識別不穩定原因
  - 對比環境差異
步驟 3: 修復環境問題
  - 統一環境配置
  - 建立穩定的測試資料
  - 使用容器化保證一致性
步驟 4: 重新執行測試
步驟 5: 建立環境健康檢查機制
```

**預防措施**:
- ✅ 使用容器化測試環境
- ✅ 建立測試環境檢查清單
- ✅ 定期同步測試資料

**預計恢復時間**: 0.5-1 天

---

### 8️⃣ DevOps - CI/CD 部署

#### 常見錯誤場景

##### 錯誤 O1: Pipeline 失敗 (W2 - P1)

**症狀**:
```
⚠️ CI/CD Pipeline 失敗:
- 建置失敗
- 測試失敗
- 部署失敗
```

**檢測時機**: CI/CD 執行時

**恢復步驟**:
```
步驟 1: 阻止後續部署 🔴
步驟 2: 分析失敗原因
  - 檢視 Pipeline 日誌
  - 識別失敗步驟
步驟 3: 快速修復
  - 建置失敗: 檢查相依性
  - 測試失敗: 檢視測試日誌
  - 部署失敗: 檢查環境配置
步驟 4: 重新觸發 Pipeline
步驟 5: 如無法快速修復,考慮回滾
```

**預防措施**:
- ✅ 本地驗證後再提交
- ✅ 使用 Pre-commit Hooks
- ✅ Pipeline 失敗時立即通知

**預計恢復時間**: 0.5-2 小時

### 9️⃣ Documentation - 文檔產出

#### 常見錯誤場景

##### 錯誤 M1: 文檔與實作不一致 (D2 - P2)

**症狀**:
```
⚠️ 文檔過時:
- API 文檔與實際 API 不符
- 架構圖與實際架構不同
- 使用指南步驟錯誤
```

**檢測時機**: 文檔審查時、使用者回饋時

**恢復步驟**:
```
步驟 1: 識別不一致範圍
步驟 2: 與開發團隊確認實際實作
步驟 3: 更新文檔
  - 優先更新 API 文檔
  - 更新架構圖
  - 更新使用指南
步驟 4: 建立文檔同步機制
  - 代碼變更時同步更新文檔
  - 使用文檔版本控制
步驟 5: 重新發布文檔
```

**預防措施**:
- ✅ 文檔與代碼放在同一 Repository
- ✅ 使用自動化文檔生成 (API Doc)
- ✅ 代碼審查時檢查文檔更新

**預計恢復時間**: 0.5-2 天

## 🎓 錯誤恢復最佳實踐 / Best Practices

### ✅ 推薦做法 (DOs)

1. **✅ 及早檢測,快速回應**
   - 在每個階段設置檢查點
   - 發現問題立即處理,不拖延
   - 小問題不放過,避免累積成大問題

2. **✅ 系統性診斷,不猜測**
   - 使用工具和數據輔助診斷
   - 找到根本原因,不只治標
   - 記錄診斷過程供後續參考

3. **✅ 有步驟地恢復,不急躁**
   - 遵循恢復步驟,不跳步
   - 每步驗證後再進行下一步
   - 必要時回滾,重新開始

4. **✅ 記錄與分享,持續改進**
   - 完整記錄錯誤與恢復過程
   - 定期召開回顧會議
   - 更新檢查清單和 SOP

5. **✅ 預防勝於治療**
   - 投資在預防機制
   - 建立自動化檢查
   - 定期進行風險評估

---

### ❌ 避免做法 (DON'Ts)

1. **❌ 不要隱瞞錯誤**
   - 發現問題立即回報
   - 不要擔心被責備而隱瞞
   - 越早發現,損失越小

2. **❌ 不要跳過診斷直接修復**
   - 不清楚原因就動手修改
   - 沒有診斷可能修錯方向
   - 可能引入新的問題

3. **❌ 不要單打獨鬥**
   - 遇到困難立即尋求協助
   - 召集相關專家協同處理
   - 利用團隊的集體智慧

4. **❌ 不要忽略預防措施**
   - 只修復當下問題就算了
   - 不更新檢查清單和流程
   - 同樣的錯誤重複發生

5. **❌ 不要在壓力下草率決策**
   - 即使時間緊迫也要冷靜分析
   - 必要時爭取更多時間
   - 草率決策可能造成更大損失
