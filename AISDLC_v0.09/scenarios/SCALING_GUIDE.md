# 專案規模化調整指引 / Project Scaling Guide

**版本 / Version**: v0.09
**建立日期 / Created**: 2025-11-10
**文檔目的 / Purpose**: 提供 AISDLC 框架在不同專案規模下的調整建議

---

## 📋 文檔概述 / Document Overview

### 目的 / Purpose

AISDLC 框架的 SOP 預設針對**中型專案**設計。本指南協助您根據專案規模調整:
1. **時間估算** - 不同規模的時程調整係數
2. **文檔詳細程度** - 文檔應該寫多詳細
3. **協作頻率** - 人機協作檢查點的密度
4. **Agent 配置** - 需要多少 Agent 參與
5. **測試策略** - 測試覆蓋率和測試類型

---

## 📏 專案規模定義 / Project Scale Definition

### 規模分類標準

| 規模 | 團隊人數 | 時程 | 代碼量 | 功能複雜度 | 使用者規模 | 範例 |
|-----|---------|------|--------|-----------|-----------|------|
| **🟢 小型** | 1-3 人 | 1-3 個月 | < 5萬行 | 簡單 | < 1000 | MVP、工具型 App、內部管理系統 |
| **🟡 中型** | 4-10 人 | 3-12 個月 | 5-50萬行 | 中等 | 1000-10萬 | 完整商業應用、SaaS 產品 |
| **🔴 大型** | 10-50 人 | 12+ 個月 | 50-500萬行 | 複雜 | 10萬-100萬+ | 企業級系統、大型平台 |
| **⚫ 超大型** | 50+ 人 | 多年 | 500萬+ 行 | 極複雜 | 100萬+ | 國際級平台、作業系統 |

### 規模評估檢查清單

快速評估您的專案屬於哪個規模：

```markdown
## 專案規模評估

**基本資訊**:
- [ ] 團隊人數: _____ 人
- [ ] 預計時程: _____ 個月
- [ ] 預估代碼量: _____ 萬行

**功能複雜度** (勾選適用項目):
- [ ] 單一功能模組
- [ ] 3-5 個功能模組
- [ ] 6-10 個功能模組
- [ ] 10+ 個功能模組
- [ ] 需要複雜的業務邏輯
- [ ] 需要分散式架構
- [ ] 需要高併發處理

**技術複雜度**:
- [ ] 單一技術棧
- [ ] 前後端分離
- [ ] 微服務架構
- [ ] 多平台 (Web/iOS/Android)
- [ ] 需要第三方整合
- [ ] 需要資料遷移
- [ ] 需要即時通訊

**使用者規模**:
- [ ] < 100 使用者
- [ ] 100-1000 使用者
- [ ] 1000-1萬 使用者
- [ ] 1萬-10萬 使用者
- [ ] 10萬+ 使用者

**評估結果**:
- 勾選 0-5 項 → 🟢 小型專案
- 勾選 6-12 項 → 🟡 中型專案
- 勾選 13-20 項 → 🔴 大型專案
- 勾選 20+ 項 → ⚫ 超大型專案
```

## 🟢 小型專案調整建議 (1-3 人, 1-3 個月)

### 時間估算調整

| 情境 | 中型專案預設 | 小型專案調整 | 調整係數 |
|------|------------|------------|---------|
| Greenfield | 3-5 天 | 1-2 天 | × 0.4 |
| Brownfield | 2-4 天 | 0.5-1.5 天 | × 0.4 |
| Refactoring | 2-3 天 | 0.5-1 天 | × 0.4 |
| Integration | 1-2 週 | 0.5-1 週 | × 0.5 |
| Testing | 1-2 週 | 0.5-1 週 | × 0.5 |
| Security | 1-2 週 | 0.5-1 週 | × 0.5 |
| Performance | 1-2 週 | 0.5-1 週 | × 0.5 |
| DevOps | 1-2 週 | 0.5-1 週 | × 0.5 |
| Documentation | 3-5 天 | 1-2 天 | × 0.4 |

### 文檔簡化建議

**核心文檔** (必須):
- ✅ **PRD** (精簡版): 2-3 頁,重點描述核心功能
- ✅ **User Stories**: 每個功能 1-2 個故事即可
- ✅ **API 規格** (如適用): 重點 API 即可,不需要每個都寫
- ✅ **測試計畫**: 簡化版,重點測試案例

**可選文檔** (依需求):
- 🟡 **FRD**: 可與 PRD 合併
- 🟡 **SRD**: 簡化為架構圖 + 技術選型說明
- 🟡 **詳細設計文檔**: 可省略,用註解取代

**完全省略**:
- ❌ **完整的業務流程圖**: 用簡單的流程圖即可
- ❌ **詳細的資料字典**: 用 Schema 註解即可
- ❌ **複雜的追蹤矩陣**: 用簡單的連結即可

### 協作頻率調整

**人機協作確認點** 🔴:
- **中型專案**: 每個階段 3-5 個確認點
- **小型專案**: 每個階段 1-2 個確認點

**建議保留的關鍵確認點**:
1. ✅ 需求確認 (PRD 完成時)
2. ✅ 技術選型確認
3. ✅ 測試計畫確認
4. ✅ 部署前確認

### Agent 配置簡化

**Greenfield 小型專案**:
- **中型專案**: PM/PO + SA + BA + SD + QA + Dev (6 個 Agents)
- **小型專案**: SA + Dev + QA (3 個 Agents)
  - SA 兼任 PM/PO + BA 角色
  - Dev 兼任 SD 角色

**Brownfield 小型專案**:
- **中型專案**: SA + Dev-Senior + Code-Analyzer + QA + SD (5 個 Agents)
- **小型專案**: SA + Dev (2 個 Agents)
  - SA 使用代碼分析工具輔助

### 測試策略調整

**測試覆蓋率目標**:
- **中型專案**: 單元測試 ≥ 80%, 整合測試 ≥ 60%
- **小型專案**: 單元測試 ≥ 60%, 整合測試 ≥ 40%
  - 聚焦核心業務邏輯
  - 手動測試佔比可提高

**測試類型**:
- ✅ **必須**: 單元測試 (核心邏輯), 整合測試 (關鍵流程)
- 🟡 **可選**: 端對端測試, 效能測試
- ❌ **可省略**: 壓力測試, 混沌測試

## 🟡 中型專案 (4-10 人, 3-12 個月)

### 基準配置

**中型專案是 AISDLC SOP 的預設目標**,無需特別調整。

**標準配置**:
- ✅ 完整的文檔產出 (PRD/FRD/SRD/API)
- ✅ 標準的 Agent 配置
- ✅ 完整的測試策略
- ✅ 標準的協作頻率

### 優化建議

**可選優化**:
1. **並行處理**: 多個功能模組可並行開發
2. **分層測試**: 單元測試、整合測試、端對端測試分層進行
3. **持續集成**: 建立 CI/CD Pipeline
4. **文檔版本控制**: 使用 Git 管理文檔

## 🔴 大型專案調整建議 (10-50 人, 12+ 個月)

### 時間估算調整

| 情境 | 中型專案預設 | 大型專案調整 | 調整係數 |
|------|------------|------------|---------|
| Greenfield | 3-5 天 | 1-3 週 | × 3-4 |
| Brownfield | 2-4 天 | 1-2 週 | × 3-4 |
| Refactoring | 2-3 天 | 1-2 週 | × 3-4 |
| Integration | 1-2 週 | 2-6 週 | × 2-3 |
| Testing | 1-2 週 | 3-8 週 | × 3-4 |
| Security | 1-2 週 | 2-4 週 | × 2-3 |
| Performance | 1-2 週 | 2-6 週 | × 2-3 |
| DevOps | 1-2 週 | 2-4 週 | × 2-3 |
| Documentation | 3-5 天 | 1-3 週 | × 3-4 |

### 文檔擴充建議

**核心文檔** (詳細版):
- ✅ **PRD**: 完整詳細,包含業務邏輯、競品分析、市場分析
- ✅ **FRD**: 詳細功能規格,包含所有邊界條件
- ✅ **SRD**: 詳細技術設計,包含架構決策記錄 (ADR)
- ✅ **API 規格**: 每個 API 都要有完整規格
- ✅ **資料字典**: 所有資料表和欄位的詳細說明
- ✅ **測試計畫**: 完整的測試策略、測試案例、測試資料

**額外文檔**:
- ✅ **架構決策記錄 (ADR)**: 記錄重要技術決策
- ✅ **風險管理計畫**: 識別風險、應對策略
- ✅ **變更管理流程**: 正式的變更申請流程
- ✅ **追蹤矩陣**: 完整的需求追蹤矩陣
- ✅ **合規文檔**: 安全合規、隱私合規文檔

### 協作頻率加強

**人機協作確認點** 🔴:
- **中型專案**: 每個階段 3-5 個確認點
- **大型專案**: 每個階段 5-8 個確認點

**額外確認點**:
- ✅ 每週進度檢查點
- ✅ 每個子模組完成確認
- ✅ 跨模組整合確認
- ✅ 利害關係人定期審查

### Agent 配置擴充

**Greenfield 大型專案**:
- **基本配置**: PM/PO + SA + BA + SD + QA + Dev
- **擴充配置**:
  - 增加 Dev-Senior (技術決策)
  - 增加 QA-Lead + QA-Automation (測試管理)
  - 增加 Security-Engineer (安全審查)
  - 增加 Performance-Engineer (效能管理)
  - 增加 DevOps-Engineer (CI/CD 管理)

**按模組組織** Agents:
- 每個主要模組配置獨立的 Agent 團隊
- 設置跨模組協調 Agent

### 測試策略加強

**測試覆蓋率目標**:
- **單元測試**: ≥ 90%
- **整合測試**: ≥ 80%
- **端對端測試**: ≥ 70%

**測試類型**:
- ✅ **必須**: 所有測試類型
  - 單元測試
  - 整合測試
  - 端對端測試
  - 效能測試
  - 安全測試
  - 壓力測試
  - 回歸測試

**測試環境**:
- ✅ Dev (開發環境)
- ✅ Test (測試環境)
- ✅ Staging (預發布環境)
- ✅ Production (生產環境)

### 專案管理強化

**必要實踐**:
- ✅ **敏捷開發**: Scrum 或 Kanban
- ✅ **Sprint 規劃**: 2-4 週 Sprint
- ✅ **每日站會**: 同步進度和阻礙
- ✅ **Sprint 回顧**: 持續改進
- ✅ **風險管理**: 定期風險評估
- ✅ **變更管理**: 正式的變更控制流程

## ⚫ 超大型專案建議 (50+ 人, 多年)

### 關鍵調整

超大型專案需要**企業級專案管理方法論**:

**組織結構**:
- ✅ 分層管理: 專案群 → 專案 → 子專案 → 功能模組
- ✅ 跨職能團隊 (Cross-functional Teams)
- ✅ 架構委員會 (Architecture Review Board)
- ✅ 變更控制委員會 (Change Control Board)

**AISDLC 應用方式**:
- ✅ 每個子專案/模組使用 AISDLC
- ✅ 統一的文檔標準和模板
- ✅ 集中式的需求管理
- ✅ 標準化的 Agent 配置

**額外流程**:
- ✅ 正式的設計審查 (Design Review)
- ✅ 代碼審查 (Code Review) 標準流程
- ✅ 架構決策記錄 (ADR) 機制
- ✅ 技術債務管理
- ✅ 知識管理系統

## 💡 規模化最佳實踐 / Scaling Best Practices

### ✅ 推薦做法 (DOs)

1. **✅ 根據實際情況靈活調整**
   - 不要死板地套用調整係數
   - 根據團隊能力和經驗調整
   - 考慮技術複雜度和業務複雜度

2. **✅ 保留核心檢查點**
   - 即使是小型專案也要保留關鍵確認點 🔴
   - 需求確認、技術選型、測試計畫、部署前確認不可省略

3. **✅ 文檔求精不求多**
   - 小型專案: 文檔簡潔清楚即可
   - 大型專案: 文檔詳細但要有清楚的目錄和索引

4. **✅ 測試策略因地制宜**
   - 小型專案: 聚焦核心邏輯測試
   - 大型專案: 分層測試、自動化測試

5. **✅ 持續監控和調整**
   - 定期檢視實際進度 vs 計畫
   - 根據實際情況調整策略
   - 記錄經驗教訓供下次參考

### ❌ 避免做法 (DON'Ts)

1. **❌ 不要低估時程**
   - 即使是小型專案也要預留緩衝
   - 考慮學習曲線和未知風險

2. **❌ 不要過度簡化文檔**
   - 即使是小型專案也要保留核心文檔
   - 未來維護時會需要這些文檔

3. **❌ 不要忽略測試**
   - 即使時程緊迫也不能跳過測試
   - 測試不足會導致更多問題

4. **❌ 不要盲目擴充團隊**
   - 大型專案不是單純增加人數
   - 需要適當的組織結構和管理機制
   - 記住「人月神話」: 增加人手可能延後進度

5. **❌ 不要忽略溝通成本**
   - 團隊人數增加,溝通成本指數增長
   - 大型專案需要更多的協調和溝通機制
