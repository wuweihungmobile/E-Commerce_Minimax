## 1. 背景

26 個 Sprint 已交付 M01–M18 並清零技術債（活躍 DEF=0、catch(Exception)=0、@Deprecated=0、@Test=668）。但專案缺正式 product backlog。PM/PO 拍板走 **方向 (b) 強化既有模組**。

**核心洞察**：後端 18 模組中 **16 個高成熟**，但**買家端前端缺一大塊** —— 訂單、付款、物流、評價、通知收件匣都是「**後端做完、沒有 UI**」。平台目前偏向 admin/seller 後台，**買家無法從 UI 完成「下單 → 付款 → 收貨追蹤 → 評價」閉環**。最高 CP 值的強化 = **把已建好的後端用前端「變現」**（高信心、中等工作量）。

## 4. 推薦 Epic：買家端體驗閉環（EPIC-BUYER）

候選 #1–#6 同屬一個主題、且**後端皆已就緒**，組成一條完整買家旅程：

```
下單(M05) → 付款(M07) → 收貨追蹤(M11) → 評價(M08)
         ↘ 通知收件匣(M09，全程狀態通知) ↙
              預訂旅宿(M06) 同享上述閉環
```

- **為何優先**：解鎖「已建好但使用者碰不到」的後端價值，高信心、可快速見效；補齊平台目前最大缺口（買家端 UI）。
- **🔴 PM/PO 決策（2026-07-01）**：採「**先補品質再加功能**」—— **Sprint 28 先做 #9 測試補強 + #8 後台深化**（為 EPIC-BUYER 打好有測試防護網的後台基礎），**EPIC-BUYER（#1–#6）自 Sprint 29 起動工**。
- **Sprint 29 ✅ 已交付**：#1 訂單前端（`ae3073b`）+ #2 通知收件匣（`31d2b5c`）+ #3 付款前端 Mock（`c2bdc17`）—— 買家閉環起手完成（下單→付款→收通知→查訂單）。
- **Sprint 30+（規劃中）**：#4 預訂管理 + #5 評價 + #6 物流前端，完成整條閉環；並手動 E2E 驗證買家旅程（AI-1401）。

### 重要前提/風險
- **M07 付款**：後端目前是 **Mock**（agent 確認 3 個 mock 方法）。付款前端可先對 Mock 做出可 demo 的流程（#3），**真實金流串接（#10）為獨立大項（13 SP + 外部依賴）**，建議單獨 Sprint 評估，不與前端 UI 綁死。
- **M14 Analytics 後端 0 測試**：深化前先補測試（#9），避免在無防護網上加功能。
