**Sprint**: Sprint 238
**日期**: 2026-10-03

## 1. 缺口盤點結果

### 1.1 起點與排程（順序為我的安排，屬推論）

[SPRINT_237_PLAN.md](SPRINT_237_PLAN.md) 完成了 `DEF-319` 的後端（訂單蓋商品所屬店鋪、購物車含多家店鋪時結帳須指定 `storeId`、否則 `E-5020`），並明說前端的分店鋪購物車與結帳畫面留給本輪：沒有它，含多家店鋪的購物車使用者只會看到 `E-5020`，無法完成結帳（單一店鋪的購物車不受影響）。本輪只做前端，後端沒有改動。

### 1.2 修復前的前端行為（讀碼）

- **購物車頁**：整車一張「訂單摘要」，促銷碼輸入一個、「前往結帳」一顆；`GET /v2/cart` 的運費、折扣、應付金額是整車一份。
- **三個結帳頁**（商品、房間、合併）：各自讀整份購物車、依項目類型篩選，送出時不帶店鋪。
- **畫面上的應付金額會過期**（既有問題，本輪順手收斂）：調整數量或移除項目時，本地只更新小計，但畫面顯示的總金額讀的是伺服器上次回傳的 `finalAmount`，所以數量改了、總金額不動。

### 1.3 設計

| 面向 | 做法 |
|------|------|
| 購物車頁 | 依後端的 `stores[]` 分組。**含多家店鋪**：每家店鋪一個區塊（店鋪名稱、該店鋪的項目、各自的摘要卡），摘要卡有自己的運費（該店鋪的運費模板）、促銷碼輸入與「前往結帳」；頂端一則說明（每筆訂單只能包含同一家店鋪的商品，請分店鋪各自結帳）；房源／商品已不存在的項目（`storeId` 為 null）另列「無法結帳的項目」，只能移除。**單一店鋪、或沒有 `stores` 的舊版回應**：維持原本「整車一張摘要」的畫面（只多一行店鋪名稱），既有的 mock 型 Playwright 規格不必改 |
| 促銷碼 | 在店鋪區塊內套用：驗證（`GET /v2/cart/validate-promo?code=…&storeId=…`）、套用（`POST /v2/cart/apply-promo`，body 帶 `storeId`）、移除（`DELETE /v2/cart/promo?storeId=…`）都帶該店鋪；輸入框與訊息以店鋪為單位（兩家店鋪各自一個，不互相覆蓋） |
| 結帳 | 「前往結帳」依**該店鋪**的項目類型導向：有商品也有房間→`/checkout/mixed`、只有商品→`/checkout/product`、只有房間→`/checkout`，網址帶 `?storeId=…`（單一店鋪的舊版購物車不帶）。三個結帳頁在載入時讀 `window.location.search` 的 `storeId`（沿用 `returns/new` 頁避開 `useSearchParams` Suspense 邊界的慣例），只處理該店鋪的項目，送出時帶 `storeId`（`POST /v2/orders`、`POST /v2/checkout/mixed`）；房間結帳頁只在送出時才讀購物車，同樣依 `storeId` 篩選 |
| 應付金額 | 摘要卡的總金額一律由「小計＋運費－折扣」即時算出，不採用伺服器上次回傳的 `finalAmount`（修掉 §1.2 的過期問題）。數量或項目變動後，每家店鋪的小計與件數在本地重算；運費與折扣沿用上次的值（它們依店鋪運費模板與促銷碼而定，要等下次載入才重算，與修復前相同） |
| 錯誤碼 | 商品結帳頁與合併結帳頁的錯誤對照補 `E-5020`：「購物車含多家店鋪的商品，請回購物車，從要結帳的店鋪區塊進入結帳」；購物車頁套用促銷碼遇到 `E-5020` 顯示「請在要使用優惠券的店鋪區塊套用」 |

## 2. 使用者決策與需要使用者知悉的行為變更

本輪沒有新的使用者決策。行為變更（皆為畫面，不動資料）：

1. **含多家店鋪的購物車從此能完成結帳**——在 Sprint 237 與本輪之間，這種購物車只會看到 `E-5020`。
2. **購物車頁的總金額改成即時算出**：調整數量後總金額會跟著動（原本不動）。運費與折扣在重新載入前仍是上次的值，與修復前相同。
3. 單一店鋪的購物車多一行「店鋪：名稱」。

## 6. 範圍外（延後）、已知限制與待決定

### 6.1 已知限制

1. **運費與折扣在項目變動後不即時重算**（見 §1.3）：數量改了以後，總金額用舊的運費與折扣算（例如免運門檻跨過去了，畫面仍顯示舊運費），要重新整理才會對。與修復前相同，沒有因本輪變差。
2. **購物車頁沒有「全部結帳」**：含多家店鋪時只能一家一家結（PRD US-008／PC-005 明文 Phase 1 不支援跨商家訂單；依店鋪拆單是 Phase 2）。
3. **沒有檢查店鋪本身的狀態**（承 [SPRINT_237_PLAN.md](SPRINT_237_PLAN.md) §6.1 第 2 點）。
4. **促銷碼輸入錯誤訊息仍是泛用文字**（「優惠券套用失敗」，只有 `E-5020` 有專屬訊息）：後端的 `E-5007`／`E-5008`／`E-5009` 在驗證那一步就以 `valid=false` 的 `invalidReason` 回來並顯示，套用那一步才失敗的情況很少見，沒有逐碼處理。
5. **前端沒有元件層測試**（見 §4）。
