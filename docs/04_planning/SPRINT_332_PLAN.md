## 2. 方法

沿用 Sprint 316～331 的慣例：①**先量測再動手**，預測在動手前登記（`predictions` 見 §8）；②**先紅後綠**——每個缺陷都先對未修的程式碼跑出紅燈並確認紅的原因對（不是測試設定的問題）；③守門本身也要被突變驗證（§5）；④相鄰缺陷只登記不順手修（§9）；⑤驗證「驗證過的狀態＝提交的狀態」：每個檢查點之後重建前端再跑測試。

### 4.4 `DEF-465`

**檔案**：新增 `lib/site.ts`（網站名稱、預設標題與三個模板常數）；根 layout 的 `title` 改成 `{ default, template }`；賣家後台與平台管理台的 layout 各加區域模板；65 個 `layout.tsx`＋33 個頁面（見 §3.3）。

**標題的組成**：

| 頁面 | 標題 |
|---|---|
| 一般頁 | `頁名｜意象若水 RUOSHUI` |
| 賣家後台 `/dashboard/*` | `頁名｜賣家後台｜意象若水 RUOSHUI` |
| 平台管理台 `/admin/*` | `頁名｜平台管理｜意象若水 RUOSHUI` |
| 首頁 | 完整品牌標題（`title.absolute`） |

區域後綴是因為「客服工單」「店鋪管理」「訂單詳情」在買家、賣家、平台三邊各有一頁。頁名依據是各頁現有的 `<h1>` 或賣家側欄標籤；認證頁的 `<h1>` 是英文（`Sign in to NextKey`…），標題用中文（整站是 `zh-TW`），列在 §10 第 3 點。動態路由用靜態的頁型名稱（「訂單詳情」「部落格文章」）——見 §9 `DEF-475`。

**開發途中踩到的坑（也是這輪最有價值的發現）**：第一版為 67 個 client 頁產生的 `layout.tsx` 寫的是 `title: '頁名'`（字串）。用 `curl` 看伺服器寫出的 `<title>`，十個抽樣裡九個對，但 `/bookings/x/payment/cancel` 的標題是 `預訂付款已取消`，**少了品牌後綴**。原因是 Next 的標題解析規則：**中間層的標題如果沒有 `template`，會把上層傳下來的 template 切斷**——`bookings/[id]/layout.tsx` 的字串標題擋在它底下的子路由前面。`tsc`、`eslint`、`next build` 都沒有任何訊號，只有看真實輸出才知道。修法：每個 `layout.tsx` 改成 `title: { default: '頁名', template: <所屬區域的模板> }`，重新宣告 template；並把這件事做成守門（§4.5）。

**逐個說明（沒有一個是「改預測湊結果」）**：

- **T01～T10（標題）**：全部第一次就吻合。重點：T02（`default` 沒經過上層的 template）同時殺掉解析模型的單元案例、「帶品牌」「區域後綴」與「不重複」共 4 個——不重複也會紅是因為「客服工單」「訂單詳情」在不同區域的 C 頁 layout 變成同一個沒有後綴的名字，登記時有推演到；**T07 重現開發時踩到的原始 bug**（把一個 layout 的 `{ default, template }` 改回字串標題），恰好只有「解析後的標題都帶品牌」紅，也就是這道守門確實能擋住當時只有瀏覽器看得到的錯誤；T09 補的是偵測器自己的洞（`'a' + 'b'` 這類運算式曾被默默讀成 `'a'`），T10 守「巢狀物件裡的 `title`（例如 `openGraph`）不算」。
- **L01～L04（失敗靜默）**：全部吻合，包含 L01（拿掉「解構了還要真的被用到」的判斷，那兩個偵測器案例紅）與 L04（登記數量比實際多，「已修好要調降登記」那條紅）。
- **B01、F01、E01、E02、M01、M02**：吻合。

## 10. 我替使用者做的決定（可一句話推翻）

1. **合併的方向**：保留 `/dashboard/posts*`、`/dashboard/media`，移除 `/cms`。理由：PRD §10.1.2 的正式路由與賣家側欄的入口、SPRINT_08 AC-007 的刪除規則都在這邊；`/cms` 專案內沒有任何連結指向它。**反例**：Sprint 9 的 `M15_CMS_FE_IMPLEMENTATION_PLAN.md` 原本打算把 `/dashboard/posts` 遷移到 `/cms`，但實際沒有完成、文件也沒有更新，PRD 後來（Sprint 253）以 `/dashboard/*` 為準。推翻的成本低：`next.config.ts` 的轉址反向、把頁面搬回去。
