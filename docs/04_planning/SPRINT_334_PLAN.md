### 3.3 讀碼＋單元層量測發現的事（影響設計）

1. **`DEF-480` 的真正原因有兩層**：①清完為空（登記時已知）；②**`updatePost` 無條件重算 slug，而唯一性檢查 `existsBySlug` 會把貼文自己算進去**——標題一個字沒改，英文標題的貼文每儲存一次就在網址後面再接一段隨機碼（`test-post` → `test-post-e1559b80`）。編輯頁每次儲存都會把標題一起送出，所以**已發布貼文的網址每存一次就變，分享出去的連結失效**。全中文標題更糟（每次都換新的隨機後備）。不一併修的話，新的 `post-<8碼>` 後備會讓問題惡化，所以這是 `DEF-480` 的必要部分，不另開編號。
2. **M18 的檔案網址是 `/api/v2/media/files/{素材編號}`**，而舊 M15 的引用檢查比對的是**儲存路徑**（`posts.featured_image_url LIKE %filePath%`）。直接把 M15 的檢查搬到 M18 抓不到 M18 形式的網址——引用檢查必須同時認「素材編號」與「儲存路徑」。
3. **舊 M15 的查詢有兩個隱患**：不分店鋪（別家店的貼文也會擋住這家店刪圖）、用 `LIKE` 會把儲存路徑裡的 `_`、`%` 當萬用字元。新查詢用 `LOCATE`＋限本店鋪。
4. **`DEF-476` 規格矛盾**：`SPRINT_08_USER_STORIES` AC-007 與 `PostService.deletePost` 自己的 Javadoc 都寫『僅 DRAFT／ARCHIVED 可刪、已發布須先下架』；但 `IT-M15-008`（Sprint 8 起）斷言已發布貼文刪除回 200，UAT／測試計畫（`TC-M15-009`、`FE-TC-008`、`AT-M15-009`）寫『先自動下架再刪除』。→ 使用者決定（§1）。**附帶發現**：`ARCHIVED` 狀態在生產程式碼裡**沒有任何入口**（沒有呼叫 `archive()` 的地方），實務上只有草稿與已發布兩種。
5. **Sprint 129（`DEF-075`）曾明確決定『員工對 media 唯讀』**——這次使用者的選擇**取代**那個決定（程式註解與 API 文件都已註明）。
6. **平台管理員刪除貼文**（`DELETE /v2/admin/posts/{id}`）與店鋪端共用 `PostService.deletePost`，所以新規則也適用（先用 `…/unpublish` 下架）。
7. `IntegrationTestConfiguration` 把兩個 `MediaService` 都換成 mock：HTTP 層的媒體測試只能驗到『授權放行』，刪除守門的真實邏輯要靠單元測試與真實 PostgreSQL 查詢測試。

## 4. 實作

### 4.1 `DEF-480` 與更新時的 slug

- `PostService`：`slugBase(title)` 保證非空（清完為空 → `post-<8碼>`）；`generateSlug`（建立）與 `generateUniqueSlug`（更新，**排除自己**）都從它出發；`updatePost` **只有標題真的改了才重算**。
- `PostCategoryService`：同樣的後備（`category-<8碼>`）與名稱沒改不重算。分類的額外後果：原本同店第二個全中文分類會因空字串 slug 重複而 `E-8014` 建立失敗。
- `V97__Backfill_Empty_Post_And_Category_Slugs.sql`：把 `slug = ''` 的列補成後備格式。**刻意不動**先前被存成 `-<8碼>` 的貼文（網址能開，改掉會讓分享出去的連結失效）。因 `posts.slug` 全平台唯一、分類每店唯一，空字串列至多各 1 列，不需處理碰撞。冪等。

### 4.2 `DEF-476`

- `PostService.deletePost`：`PUBLISHED` → 409 `E-4107`（新碼，加入 `GlobalExceptionHandler` 的 409 組與 `API_Error_Codes.md`）。
- 前端：貼文列表與編輯頁的刪除鈕在已發布時 `disabled`（附 `title` 說明）；刪除失敗的 toast 改顯示後端訊息（`apiErrorMessage`），不再一律『稍後再試』。列表原本 `!== 'DRAFT'` 改為 `=== 'PUBLISHED'`，與後端一致（`ARCHIVED` 可刪，雖然目前沒有入口）。

### 4.3 `DEF-474`

- **權限**：`RolePermissionMapping` 讓 `STORE_STAFF`／`SELLER`／`HOST` 擁有 `media:read／create／update／delete`（與 `STORE_OWNER` 相同）。我多給了 `update`（選項只寫『上傳與刪除』）：媒體中心頁有編輯詮釋資料的功能，只給上傳／刪除會出現『能傳、不能改』的半套畫面。
- **刪除守門**：`MediaService.deleteAsset` 先查本店鋪是否有貼文的封面圖網址含該素材的**編號**或**儲存路徑**，有則 409 `E-8020`（新碼）、不軟刪除。查詢是 `PostRepository.existsByTenantIdAndFeaturedImageUrlReferencing`（`LOCATE`、限本店鋪）；空白的儲存路徑不拿去查（`LOCATE('', x)` 恆為真，會讓所有素材都刪不掉）。
- **移除**：`PostController` 的 5 個 `/v2/dashboard/media/*` 端點、`core.cms.media.MediaService`／`MediaUploadService`、`M15Dto` 的三個媒體 DTO、舊的 `existsByFeaturedImageUrlContaining`、`IntegrationTestConfiguration` 裡的 M15 媒體 mock，以及它們專屬的測試（`core/cms/media/MediaServiceTest`、`MediaUploadServiceTest`、`PostControllerE2ETest` 的 5 個媒體案例、`PostControllerFilterValidationTest` 的媒體案例）。`core.cms.media.MediaValidationService` **保留**（M18 仍用它）。

## 7. 行為變更與已知限制

### 7.1 行為變更

1. **已發布的貼文不能直接刪**：店鋪端與平台管理員端都一樣（409 `E-4107`）；列表與編輯頁的刪除鈕不可按。
2. **`STORE_STAFF`／`SELLER`／`HOST` 可以上傳、更新、刪除媒體**（取代 Sprint 129 的『員工唯讀』）。
3. **被本店鋪貼文封面圖使用的媒體不能刪**（409 `E-8020`）。
4. **`/v2/dashboard/media/*` 五個端點消失**（現在回 404／405）。前端自 Sprint 332 起就沒有呼叫者。
5. **貼文／分類 slug 不再是空字串**；標題（名稱）沒改的儲存不換網址。全中文標題的貼文網址是 `/blog/post-<8碼>`（不是有意義的拼音）。
6. 既有 `slug = ''` 的列由 V97 補成後備格式。

### 7.2 已知限制（誠實列出）

1. **引用檢查只看貼文封面圖**，不掃貼文內文（Markdown 裡的圖）。內文引用的素材被刪後，內文的圖會壞掉 → `DEF-481`。
2. **M18 的檔案網址需要登入**（`SecurityConfig` 的公開清單沒有 `/v2/media/files/**`；憑證存在瀏覽器 localStorage，`<img>` 帶不出去）。**讀碼推論，未量測**：貼文封面圖若用媒體中心的網址，公開部落格可能顯示不出來。這個問題原本就存在（舊 M15 的檔案端點也要登入），不是這輪造成的 → `DEF-482`。
3. **沒有任何路徑會刪除儲存層的實體檔案了**：舊 M15 的刪除會連 MinIO 物件一起刪，M18 只做軟刪除。M15 的刪除原本就沒有前端呼叫者，實務上沒有退步，但被刪除的素材會留在儲存層。
4. 既有的 `-<8碼>` slug（開頭有連字號）沒有遷移（見 §4.1）。
5. 前端的『刪除失敗顯示後端訊息』沒有專屬案例（`apiErrorMessage` 的一般行為由既有測試守）；刪除鈕 `title` 說明文字沒有被斷言。
6. 新增的 E2E 沒有對未修的程式碼跑出紅燈（見 §3.2 說明），靠突變證明鑑別力。
7. 沒有做目視檢查（這輪前端只動兩個按鈕的 `disabled`）。
