## 2. 做得好的（What went well）

- **意識到「租戶擁有權」不是萬用模式，主動識別本次是不同的擁有權語意**：這個 codebase 過去十幾個 Sprint 反覆修的都是「租戶擁有權檢查」漏洞，容易形成慣性反射。這次動手前先確認地址簿的本質——買家可能向多個不同租戶下單，地址簿是全域個人資料，與租戶無關——因此刻意採用「僅比對 `userId`」的擁有權模式，並在 `AddressService`/entity 的 Javadoc 明確記錄這個決策理由，避免自己或未來的人依慣性誤判為「忘記加租戶檢查」而錯誤修改。
- **訂單收件資訊維持 snapshot 語意，不因新功能改變既有正確設計**：設計 `OrderDto.CreateRequest.addressId` 整合時，沒有把 `Order` 的收件欄位改成外鍵關聯到 `Address`（表面上更「正規化」），而是維持現有自由文字欄位、在下單當下複製地址內容進去——因為訂單是歷史記錄，若改成外鍵，使用者事後編輯或刪除地址簿項目會回頭影響已建立訂單的歷史收件資訊，這是不可接受的副作用。
- **發現重複邏輯立即抽共用方法，而非各自複製**：一開始在 `OrderService` 內直接複製了一份 `AddressService.findOwnedAddress` 的擁有權判斷邏輯，動手測試前意識到這是重複程式碼，隨即在 `AddressService` 新增 `public getOwnedAddress` 方法給 `OrderService` 重用並移除重複實作，而非讓兩份邏輯各自演化、日後修一邊忘了修另一邊。
- **老實揭露驗證方法的邊界，不假裝做了實際沒做的事**：本次工具集沒有瀏覽器自動化能力，無法真正「在瀏覽器中操作」新頁面。沒有含糊其辭或聲稱「已測試 UI」，而是明確記錄實際做了什麼（後端真實 HTTP E2E 全流程、前端 `npm run build`/`eslint`/路由掛載確認）與沒做什麼（人工互動式瀏覽器操作），寫入 Sprint 完成記錄。

## 3. 待改善的（What to improve）

- **意外發現「PRODUCT 商品訂單前端結帳流程完全沒有串接」這個比地址簿本身更大的既有缺口，但只記錄未處理**：探查時發現前端 checkout 頁面只服務 Booking（訂房）流程，`/v2/orders`（商品訂單建立）在前端找不到任何呼叫點——即使地址簿後端 API 已完成，若沒有 PRODUCT checkout 頁面，`addressId` 欄位在買家真實購物流程中目前無法被實際使用到（只能透過 API 直接呼叫或未來頁面串接時使用）。這次判斷此缺口範圍遠超地址簿主題、決定不擴大範圍處理，但也代表本 Sprint 交付的後端能力目前缺乏對應的真實使用場景，需要在候選清單中提高「PRODUCT 結帳串接」的優先度。
- **前端沒有現成的「帳戶設定」容器頁**，這次是直接開一個扁平路由 `/addresses` 並在 Header 加連結，若未來還有更多買家個人資料類功能（如通知偏好、個資編輯），會需要重新評估是否該收攏成一個「帳戶」母頁面/選單，而不是持續在 Header 疊加平行連結。
