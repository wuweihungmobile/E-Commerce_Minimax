## 4. 矛盾修復

### 4.1 API 版本策略統一

| 變更項目 | 原始內容 | 改善後內容 |
|---------|---------|-----------|
| **M05 訂單 API** | §9 為 `/api/orders`，§15 為 `/api/v1/orders` | **統一為 `/api/v2/orders`** |
| **M06 預訂 API** | `/api/v1/bookings` | **更新為 `/api/v2/bookings`** |
| **所有新 API** | `/api/v2/*` | **保持不變** |

**調整理由**：統一使用 `/api/v2/` 前綴，消除跨章節不一致。

### 4.2 Test Case 編號修正

| 變更項目 | 原始內容 | 改善後內容 |
|---------|---------|-----------|
| **§15.2.1 TC-M05-006** | 重複（並發防護 + 無效 JWT） | **拆分為 TC-M05-006（並發）、TC-M05-007（無效 JWT）** |
| **§15.2.1 TC-M05-007** | 重複（庫存為0直接失敗 + totalAmount篡改） | **拆分為 TC-M05-008（庫存為0）、TC-M05-009（totalAmount篡改）** |

**調整理由**：消除編號衝突，確保 Test Case 可追溯性。

### 4.3 M06 Phase 描述澄清

| 變更項目 | 原始內容 | 改善後內容 |
|---------|---------|-----------|
| **§6.4 M06 優先級** | P0 | **P0（GET/取消）/ Phase 2（POST 建立）** |
| **§6.6 M15 關於 M06** | M06 P0 | **澄清：M06 在 Phase 1 僅開放 GET 查詢和取消，POST 建立預訂屬 Phase 2** |

## 5. 新增需求

### 5.1 Payment Mock API 實作細節（新增 §6.10）

| 項目 | 內容 |
|------|------|
| **新增位置** | §6.10（Payment Mock API 規格） |
| **原因** | Phase 1 支付環節為 Mock，需明確定義實作方式 |

**Payment Mock API 規格**：

| 欄位 | 說明 |
|------|------|
| Mock 模式 | 系統自動將訂單狀態推進至 CREATED(=PAID) |
| Mock 回應格式 | `{ "paymentId": "mock_xxx", "status": "SUCCESS", "mock": true }` |
| 模擬失敗 | 透過 `X-Mock-Fail: true` Header 模擬支付失敗（用於測試） |
| Phase 1 退款 | 不支援，始終回傳 E-4013 |

### 5.2 開店申請表單欄位（新增至 §9.10）

| 欄位 | 類型 | 必填 | 說明 |
|------|------|------|------|
| storeName | String | ✅ | 店鋪名稱 |
| storeDescription | String | ❌ | 店鋪描述 |
| businessType | Enum | ✅ | RETAIL_ONLY / BOOKING_ONLY / HYBRID |
| contactEmail | String | ✅ | 聯絡 Email |
| contactPhone | String | ❌ | 聯絡電話 |
| businessLicenseUrl | String | ❌ | 營業執照 URL（Phase 2） |
| idNumber | String | ❌ | 身分證字號（Phase 2 KYC） |
